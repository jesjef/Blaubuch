entfallen, alles kommt in einem Zug. Entscheide darin sind mit Jeffrey

Grundlage sind zwei Wunschlisten — Jeffreys eigene und ein ausführlicher

## Der Zuschnitt: nur Buchhaltung

Jeffreys Regel, wörtlich: *„Es sollte nur für die Buchhaltung optimiert sein.
Alles was mehr darüber geht → für später FinSicht."*

Das ist die Trennlinie, an der jeder Vorschlag gemessen wird. Buchhaltung
heisst: Bewegungen erfassen, ordnen und aufsummieren. Alles, was in die
Zukunft rechnet oder Vermögen bewertet, gehört nicht hierher.

**Bewusst nicht gebaut, obwohl gewünscht:**

| Vorschlag | Warum nicht |
|---|---|
| Sparziele mit Zielbetrag, Zieldatum, Rate, Ampel | rechnet in die Zukunft — Planung, nicht Buchhaltung |
| Vermögensverlauf über Monate als Kennzahl | bewertet Vermögen; der *Kontostand* bleibt, die *Vermögenszahl* geht |
| Zweckklassen für Bestände (zweckgebunden / Reserve / Aufbau) | Vermögensverwaltung; der Kontoname trägt den Zweck ohnehin |
| Anlagekonten mit getrennter Kursbewegung | Marktbewertung |
| Fremdwährung mit Kurs | README sagt bewusst: alles ist CHF |
| Deckungscheck Topf gegen Ausgabe | hängt an den Sparzielen |
| Sollbudget je Kategorie (Plan gegen Ist) | ein Plan ist keine Buchung |
| Offene Forderungen | verändert keine einzige Zahl, wäre ein Merkzettel neben dem Restwert — und „das Dashboard bleibt ruhig" ist eine harte Regel. Zurückgestellt, nicht verworfen |

Das ist Niklas gegenüber ehrlich zu benennen: seine eigene Top-3 lautet
A1, A2, A4 — **zwei davon fallen durch diesen Filter**. Blaubuch wird sein
Portfolio-Dokument nicht ersetzen. Was bleibt, ist dafür der stärkste Punkt
seines ganzen Berichts.

## A — Konten und Buchungen

### Der Befund, der kein Wunsch ist

Niklas hat vorgerechnet, dass sechs seiner neun Daueraufträge Umbuchungen auf
eigene Konten sind — **1'730 Fr. im Monat, die sein Vermögen nicht
verlassen.** `totals()` zieht sie als Kosten ab und senkt damit Restwert und
Sparquote.

Nachgemessen und bestätigt: `kosten = da + fix + kk + re`,
`rest = einnahmen − kosten`. Die Klassifizierung wirkt nur auf `byTag`;
`rest` und `sparquote` sehen eine grün markierte Zeile trotzdem als weg.

Das ist kein fehlendes Feature, das ist eine falsche Zahl. Ausgerechnet die
App, die bei den Einnahmen sorgfältig darauf achtet, dass ein Darlehen die
Sparquote nicht schönt, macht sie bei den Ausgaben ohne Not zu schlecht.

### Die Regel

Niklas' Zuspitzung wird übernommen, sie ist besser als der alte Vorschlag:

> Geht das Geld auf ein Konto, das Blaubuch führt, ist es eine **Umbuchung**.
> Geht es irgendwohin, wo Blaubuch nichts sieht, ist es eine **Ausgabe**.

Damit entfällt die früher geplante Warnung bei gleichem Betrag im selben
Monat — die Frage stellt sich nicht mehr.

**Daraus folgt der wichtigste Entwurfsentscheid:** eine Umbuchung ist keine
eigene Liste, sondern eine gewöhnliche Zeile **mit Zielkonto**. Ein
wiederkehrender Dauerauftrag auf das eigene Sparkonto ist damit automatisch
eine wiederkehrende Umbuchung, ohne dass es einen zweiten Mechanismus braucht.

### Der Kontenstamm

Konten sind **Stammdaten**, nicht Monatsfelder:

```js
konten: [ { id, name, institut, art, aktiv } ]
//                            art: erwerb | bestand | geliehen
```

Der **Saldo hängt am Monat**, nicht am Konto. Er wird gerechnet:

```
Endbestand = Anfangsbestand + Eingänge − Ausgänge ± Umbuchungen
```

### Fortschreibung: Vorschlag statt Automatik

Jeffreys Einwand war, dass „Konto aktuell" seinen Job tut, aber nur einmalig.
Das ist keine Modellfrage, sondern Tipparbeit.

**Entschieden: keine Einstellung, ein Modell.** Beim Anlegen eines neuen
Monats steht der Endbestand des Vormonats als **Vorschlagswert** im
Anfangsbestand — überschreibbar mit einem Tastendruck.

Eine Einstellung hätte zwei Bedeutungen für dasselbe Feld erzeugt, zwei
Rechenwege, zwei Testreihen — und im „falschen" Modus erzeugt eine vergessene
Buchung stillschweigend falsche Salden. Mit dem Vorschlagswert fällt die
Tipparbeit weg, und wer eine Buchung vergisst, korrigiert eine Zahl, statt
eine falsche Kette zu erben. Will Jeffrey später strenge Fortschreibung, trägt
das Datenmodell sie bereits — dann ist es eine Anzeigefrage, keine Migration.

### Zeilen

```js
{ id, name, betrag, klasse, vonKonto, nachKonto, aktiv, tag, laeuftBis, notiz }
```

- **`nachKonto` gesetzt** → Umbuchung. Zählt nicht zu den Kosten. Die
  Klassifizierung dient nur der Darstellung.
- **`vonKonto`** → woher es geht. Ohne diese Angabe stimmt kein Kontosaldo.
- **`aktiv: false`** → pausiert. Betrag bleibt erhalten. Niklas' B7, und
  dieselbe Begründung wie bei den Konten: ein Betrag von 0 verliert die
  Information „normalerweise 500".
- **`tag`** → Tag im Monat. Jeffreys Ausführdatum und Lohndatum.
- **`laeuftBis`** → `YYYY-MM`. Beim Anlegen des Folgemonats fällt die Zeile
  weg, statt still weiterzulaufen.
- **`notiz`** → der Grund hinter der Zahl. Kostet fast nichts und ist in der
  Buchhaltung der Verwendungszweck.

Einnahmezeilen tragen ein **Zielkonto** — damit ist Jeffreys gesplitteter Lohn
abbildbar (zwei Zeilen, zwei Konten).

## B — Klassifizierungen

Vier statt drei, eigene dazu erfindbar, und **drei Wirkungen statt zweier**:

```
verloren    das Geld ist weg          Ausgaben
erhalten    liegt woanders            Investition · Sparen · Investition blockiert
durchlauf   gehört mir gar nicht      zurückgezahlte Auslagen, fremdes Geld
```

`wirkung` ist das eigentliche Feld, die Farbe nur das Etikett. Durchlaufgeld
zählt weder ins Einkommen noch in die Kosten noch in den Restwert, bleibt aber
sichtbar — Niklas' B1. Ein Wahrheitswert `verloren: true|false` hätte das
nicht ausdrücken können, und es später nachzuziehen wäre eine zweite
Migration gewesen.

**Keine Einstellung dafür.** Eine Einstellung, die ein Konzept versteckt, ist
schlimmer als das Konzept.

Die Umschlüsselung bleibt wie geplant: **gelb → blockiert (lila)**, gemeldet
über `repariert`. Farben kommen aus einer geprüften Auswahl, nicht aus einem
Farbrad; `npm run check:farben` rechnet Kontrast und Abstand nach.
