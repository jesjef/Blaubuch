# Blaubuch 1.1.0 — Plan

Stand: 2026-08-26. Entscheidungen darin sind mit dem Benutzer abgestimmt;
offene Punkte stehen am Ende und sind als solche gekennzeichnet.

## Was hineinkommt

| | Bereich | Kern |
|---|---|---|
| **A** | Konten | Freie Einnahme- und Bestandszeilen statt fünf fester Felder, ein- und ausschaltbar, mit Umbuchung |
| **B** | Klassifizierungen | Vier statt drei, eigene dazu erfindbar, mit Farbe |
| **C** | Linux | AppImage und RPM aus der CI |
| **D** | Mitlaufend | Electron 44, toter Code, Restpunkte aus dem Sicherheitsdurchgang |

A und B ändern beide das Dateiformat. Sie gehören deshalb in **eine**
Schema-Umstellung 4 → 5 und in eine Fassung — zwei Migrationen
hintereinander wären doppeltes Risiko für dieselben Daten.

## Vorbedingung: 1.0.x abschliessen

sich ein Verpackungsproblem und ein Formatwechsel in derselben Fehlersuche.

3. `v1.0.3` veröffentlichen, Entwurf `v1.0.2` verwerfen.

## A — Konten

### Heute

`einnahmen` ist ein Objekt mit fünf festen Schlüsseln, die in drei
verschiedene Bedeutungen zerfallen:

```js
einnahmen: { netto, spesen, konto, bar, fremdschulden }
//           └── Erwerb ──┘  └ Bestand ┘  └ Geliehen ┘
```

Der Unterschied ist nicht kosmetisch: die Sparquote misst **nur am
Erwerbseinkommen**. Ein Darlehen darf sie nicht verbessern.

### Neu

Eine Liste wie bei den Kreditkarten, mit zwei zusätzlichen Feldern:

```js
konten: [
  { id, name: "Nettolohn",   betrag, art: "erwerb",   aktiv: true },
  { id, name: "Sparkonto",   betrag, art: "bestand",  aktiv: true },
  { id, name: "Darlehen",    betrag, art: "geliehen", aktiv: false }
]
```

`art` ist Pflicht und nicht frei erfindbar. Sie entscheidet, wie die Zeile
in `totals()` einfliesst — das ist Rechenlogik, keine Beschriftung. Drei
Werte: `erwerb`, `bestand`, `geliehen`.

`aktiv: false` heisst: Zeile bleibt sichtbar samt Betrag, zählt aber nicht.
Das ist bewusst etwas anderes als `betrag: 0` („läuft diesen Monat nicht"):
man kann damit durchspielen, wie der Monat ohne eine bestimmte Quelle
dasteht, ohne den Betrag zu verlieren.

### Migration 4 → 5

| alt | neu | `art` |
|---|---|---|
| `netto` | „Nettolohn" | `erwerb` |
| `spesen` | „Spesen" | `erwerb` |
| `konto` | „Kontostand" | `bestand` |
| `bar` | „Bargeld" | `bestand` |
| `fremdschulden` | „Geliehen" | `geliehen` |

Alle fünf wandern mit, auch wenn sie 0 sind — sonst verschwinden nach dem
Öffnen Zeilen, die der Benutzer kennt. Alle `aktiv: true`. `migrate()` meldet
die Umstellung über `repariert`, wie schon bei den Kreditkarten in Schema 4.

### Umbuchung

Eigene Liste je Monat, **ausserhalb** der Kostenrechnung:

```js
umbuchungen: [ { id, von: kontoId, nach: kontoId, betrag, notiz } ]
```

Sie verändert die Summe der verfügbaren Mittel **nicht** — es hat nichts
das Haushaltsbudget verlassen, das Geld liegt nur woanders. Sie verändert
nur, wie sich der Bestand auf die Konten verteilt.

**Hier liegt die eine ungeklärte Stelle**, und der Benutzer hat sie selbst
benannt: eine Umbuchung auf ein Sparkonto ist wirtschaftlich dasselbe wie
eine als „Sparen" markierte Ausgabe. Beides zugleich zu erfassen zählt
doppelt. Vorschlag:

- Die Umbuchung trägt **keine** Klassifizierung und geht nicht in
  „was ist verloren" ein.
- Wer Sparen als Fluss sehen will, erfasst es als Ausgabe mit der
  Markierung *Sparen* — dann taucht es im Geldfluss auf.
- Beide Wege stehen offen, aber nicht für denselben Betrag. Die Oberfläche
  warnt, wenn im selben Monat eine Umbuchung und eine Sparen-Ausgabe über
  denselben Betrag stehen.

Das ist der Teil, den der Benutzer nach dem Bau von Hand durchspielen
will, bevor er als fertig gilt.

### Was zu ändern ist

| Datei | Was |
|---|---|
| `budget.mjs` | `emptyMonth`, `totals`, `monthFromPrevious`, `migrate`, `buildReport`, `buildInsights` |
| `fluss.mjs` | `herkunft()` liest die Konten statt der festen Felder |
| `app.mjs` | Einnahmekachel wird eine Liste wie die Kreditkarten; Umbuchungskachel neu |
| `styles.css` | Zeile für inaktive Konten (gedämpft, nicht versteckt) |

## B — Klassifizierungen

### Heute

```js
TAGS = ["rot", "gruen", "gelb"]
rot = Konsum · gruen = Investition (Kontrolle) · gelb = Investition (blockiert)
```

Die Farben liegen als feste Hex-Werte in `styles.css`, je einmal für hell
und einmal für dunkel.

### Neu

Klassifizierungen werden Daten, nicht Konstanten. Sie liegen im Stammsatz,
nicht im Monat — eine einmal angelegte Klasse gilt überall:

```js
klassen: [
  { id: "rot",   name: "Ausgaben",              ton: 22,  verloren: true  },
  { id: "gruen", name: "Investition",           ton: 150, verloren: false },
  { id: "gelb",  name: "Sparen",                ton: 85,  verloren: false },
  { id: "lila",  name: "Investition blockiert", ton: 305, verloren: false }
]
```

**`verloren` ist das eigentliche Feld.** Die Farbe ist Beschriftung; ob ein
Betrag das Vermögen mindert oder nur verschiebt, ist die Rechnung. Eine
selbst erfundene Klasse muss das mit angeben, sonst kann `totals()` sie
nicht einordnen. Die Oberfläche fragt es beim Anlegen als eine Ja/Nein-Frage
in Worten: *„Ist dieses Geld danach weg, oder liegt es nur woanders?"*

Zeilen verweisen künftig über `klasse: <id>` statt `tag: "rot"`.

### Migration 4 → 5 — die heikle Stelle

Gelb bedeutet heute *Investition gebunden*. In der neuen Ordnung heisst
Gelb *Sparen* und Lila *Investition blockiert*. Ohne Umschlüsselung würden
alte Zahlen rückwirkend etwas anderes bedeuten.

| alt | neu |
|---|---|
| `rot` | `rot` (Ausgaben) |
| `gruen` | `gruen` (Investition) |
| **`gelb`** | **`lila`** (Investition blockiert) |

Sparen fängt leer an. `migrate()` meldet über `repariert`, wie viele Zeilen
umgeschlüsselt wurden — nicht als stille Änderung.

### Farbe

Die vier festen Töne kommen aus dem bestehenden Bestand, Lila kommt dazu.
Eigene Klassen wählen **nicht** frei aus einem Farbrad, sondern aus einer
geprüften Auswahl von Tönen. Grund: die Farben müssen in hell **und** dunkel
gegen `--ground` und `--field` lesbar bleiben, und ein frei gewählter Ton
kann das nicht garantieren.

Umsetzung: aus den festen Hex-Werten werden `oklch(L C ton)` mit je einer
Helligkeit und Sättigung pro Darstellung. Der Ton ist die einzige
Stellschraube — dieselbe Methode, die das Farbschema mit `--h` schon
benutzt.

**Abnahmekriterium, messbar:** jeder angebotene Ton erreicht in beiden
Darstellungen mindestens 3:1 gegen die Fläche, auf der er sitzt. Ein
Prüfskript rechnet das aus und läuft in der CI mit — kein Auge, ein Wert.

### Löschen

Eine Klasse, die in einem Monat noch benutzt wird, wird nicht gelöscht,
sondern stillgelegt: sie verschwindet aus der Auswahl, bleibt aber an den
alten Zeilen. Sonst verlören alte Monate ihre Bedeutung.

## C — Linux

Gewählt: **AppImage** und **RPM**. DEB und Flatpak bleiben aussen vor.

```json
"linux": {
  "target": ["AppImage", "rpm"],
  "icon": "build/icon.png",
  "category": "Office",
  "artifactName": "Blaubuch-${version}.${ext}"
}
```

CI: `ubuntu-latest` kommt in die Matrix. Analog zu macOS in benannte
Einzelschritte zerlegt, mit einem Prüfschritt, der zählt statt zu hoffen:

```bash
test -f dist/*.AppImage && test -x dist/*.AppImage
rpm -qp --queryformat '%{NAME} %{VERSION} %{ARCH}\n' dist/*.rpm
anzahl=$(ls -1 dist/*.AppImage dist/*.rpm | wc -l)
test "$anzahl" -eq 2
```

Der Datenpfad `~/.config/Blaubuch/blaubuch.json` steht bereits im README
und stimmt.

**Grenze, die benannt gehört:** die CI baut auf Ubuntu und kann nur prüfen,
dass die Pakete entstehen und formal stimmen. Ob Blaubuch auf Fedora
tatsächlich startet, prüft der Benutzer auf seinem eigenen System — die
macOS-Sache hat gezeigt, was ein grüner Bau ohne echten Start wert ist.

## D — Was mitläuft

- **Electron 40 → 44.** `npm audit` meldet GHSA-9f4c-93c8-jc8g (*high*) für
  40.x. Ausnutzbar ist es hier praktisch nicht — keine iframes, CSP
  `default-src 'none'` — aber SECURITY.md schreibt selbst, die Version aktuell
  zu halten. Eine Nebenversion ist der richtige Ort für einen
  Hauptversionssprung der Abhängigkeit; in einem Korrekturrelease wäre er falsch.
- **`samePassword` entfernen.** Wird exportiert und getestet, vom Programm
  aber nirgends benutzt. Toter Code in der Kryptoschicht.
- **Einstellungstext nachziehen.** „Rot, Grün und Gelb bleiben den
  Markierungen vorbehalten" stimmt mit Lila und eigenen Klassen nicht mehr.

## Reihenfolge

1. Schema 5 in `budget.mjs` — `migrate()` zuerst, mit Tests gegen echte
   Dateien aus Schema 3 und 4. Nichts an der Oberfläche, bevor die
   Umstellung steht.
2. Konten in Rechenkern und Geldfluss.
3. Klassifizierungen in Rechenkern und Farbsystem, samt Kontrastprüfung.
4. Oberfläche für beides.
5. Umbuchung — zuletzt, weil sie auf beidem aufsetzt.
6. Linux in die CI.
7. Electron 44, dann die volle Testreihe.

Schritt 1 ist der einzige, bei dem ein Fehler bestehende Daten beschädigt.
Er bekommt deshalb die meisten Tests und geht zuerst.

## Testplan

| Was | Wie |
|---|---|
| Migration 4 → 5 | Feste Beispieldateien in `test/fixtures.mjs`, Feld für Feld geprüft |
| Gelb → Lila | Eigener Test: keine Zeile behält nach der Umstellung `gelb` |
| Sparquote | Ein deaktiviertes Erwerbskonto senkt sie, ein deaktiviertes Bestandskonto nicht |
| Umbuchung | Summe der verfügbaren Mittel vor und nach der Umbuchung identisch |
| Eigene Klasse | `verloren: true` erhöht den Verlust, `false` nicht |
| Farbkontrast | Skript rechnet jeden Ton gegen beide Flächen in beiden Darstellungen |
| Linux | Paketdateien vorhanden, RPM-Kopfdaten lesbar |

## Risiken

| Risiko | Gegenmassnahme |
|---|---|
| Migration beschädigt Daten | `migrate()` wirft nie; vor dem Übernehmen wird eine Sicherung angelegt; Rückgängig bleibt möglich |
| Gelb-Umdeutung fällt niemandem auf | `repariert` nennt die Anzahl beim Öffnen, nicht nur im Wartungsprotokoll |
| Eigene Farben werden unlesbar | Auswahl statt Farbrad, Kontrast in der CI gerechnet |
| Doppelzählung Umbuchung/Sparen | Warnung bei gleichem Betrag im selben Monat; vom Benutzer von Hand durchzuspielen |
| Electron 44 bricht etwas | Als letzter Schritt, nach allem anderen — dann ist die Ursache eindeutig |

## Offen

- **Umbuchung und Klassifizierung.** Der Vorschlag oben ist ein Vorschlag.
  Der Benutzer will das gebaut sehen und dann selbst durchspielen; die
  endgültige Regel entsteht daraus, nicht davor.
- **Konten über Monate hinweg.** Heute ist jeder Monat für sich. Wenn Konten
  eine Bezeichnung tragen, liegt die Frage nahe, ob ein Kontostand von
  Monat zu Monat fortgeschrieben werden soll. Nicht Teil von 1.1.0 —
  hier notiert, damit die Datenstruktur es später nicht verbaut.
